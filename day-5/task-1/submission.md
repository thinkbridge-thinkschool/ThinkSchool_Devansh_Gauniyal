## Notes for mentor
Built a new, self-contained ASP.NET Core minimal API (`TraceDemo`, EF Core + SQLite, Serilog, OpenTelemetry exporting to a local Jaeger instance over OTLP) with three endpoints: `/authors/slow` (a real N+1 -- one query per author), `/authors/sleep` (a `Thread.Sleep(1500)`), and `/authors/fast` (always efficient, the control). Traced `/authors/slow` before the fix at 66.07ms with 32 total spans (1 root + 31 database round trips, one per seeded author). After the fix -- switching the endpoint to a single `Include`-based query -- the same trace shape dropped to 1.16ms with 2 total spans (1 root + 1 round trip, 170µs). The N+1 method was kept in the codebase as a regression-test fixture: an xunit test using a custom `DbCommandInterceptor` confirms it issues exactly 31 round trips against exactly 1 for the fixed method, while both return byte-identical data. First commit `8b2c2d49f051a409eedaa98a68ec21b6d370751b`, second commit is this same commit (a commit can't contain its own hash inside its own tree, so see `git log -1` or the GitHub commit view for its exact hash). The bonus KQL query was written from knowledge of the App Insights `requests` table schema and reviewed, but not run live -- this project only sends telemetry to local Jaeger, and no Azure resource was created. This is a new, self-contained project rather than a change to the shared day-3/task-3 API because that API has no EF Core and five Day 4 test projects depend on it unchanged, so adding EF Core there would risk already-completed work.

## What did you learn this session?
I learned how differently the same symptom -- a slow endpoint -- looks inside a trace depending on its cause. The N+1 query showed up as a long row of many small, nearly identical spans stacked one after another, while the Thread.Sleep showed up as one long span with nothing at all underneath it. Watching the span count drop from 32 to 2 after the fix made "round trips" a concrete, countable thing instead of just a phrase from a textbook.

## What would break this?
The OTLP exporter would silently drop every trace if Jaeger weren't running or if `OTEL_EXPORTER_OTLP_ENDPOINT` pointed somewhere wrong, and the app would give no error either way -- it would just look fine while producing zero observability. The `OpenTelemetry.Instrumentation.EntityFrameworkCore` package is the only reason the N+1 was visible as separate database spans at all, and it has never had a stable release. And since the N+1 and single-query methods return byte-identical JSON, only the round-trip-counting test could ever catch someone quietly reintroducing the per-author loop -- an ordinary data-correctness test would stay green the whole time.
