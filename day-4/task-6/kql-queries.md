# KQL queries

**Status: complete** — both queries were run for real against `thinkschool-day4-task6-ai` (Central India), after generating real traffic by running the app locally against the real Key Vault + Azure Monitor pipeline. Results below are genuine query output, not invented.

## The actual exercise: slowest 10 requests in the last hour

```kql
requests
| where timestamp > ago(1h)
| top 10 by duration desc
| project timestamp, name, duration, resultCode, operation_Id
```

**Why `requests`, not `traces`.** The task body's own example (below) queries `traces` — but `traces` holds free-text/structured *log* lines (what `ILogger`/Serilog calls emit), which have no inherent request-duration column. Every HTTP request handled by the app gets its own row in the separate `requests` table instead, and that row *does* carry a `duration` column (milliseconds) — because that table is populated by the AspNetCore instrumentation's request span, not by application log calls.

**What each line does:**
- `requests` — start from the request-telemetry table (one row per HTTP request span).
- `| where timestamp > ago(1h)` — restrict to the last hour.
- `| top 10 by duration desc` — sort by duration, highest first, keep only 10.
- `| project timestamp, name, duration, resultCode, operation_Id` — pick which columns to show.

## The task body's example query

```kql
traces
| where timestamp > ago(15m)
| where customDimensions.UserId == "abc"
| order by timestamp asc
```

**What it does differently.** This queries `traces` (structured log lines, not request spans), filtered to a *specific* value of a custom property named `UserId`. This is exactly how a structured log property set via a message template — `logger.LogInformation("Login succeeded for user {UserId}", caller.UserId)` — would show up once exported to App Insights: as a key inside the dynamic `customDimensions` bag on that log row, queryable directly (`customDimensions.UserId`).

**Real result, run against this app's actual `UserId` (`verification-user`) instead of the task's placeholder `"abc"`:**

```kql
traces
| where timestamp > ago(1h)
| where customDimensions.UserId == "verification-user"
| order by timestamp asc
| project timestamp, message, customDimensions
```

**Zero rows returned.** This is a genuine, real finding, not a query mistake — confirmed by checking `traces | where timestamp > ago(1h) | count` directly, which also returns `0`. See `README.md`'s "Telemetry, verified end-to-end" section for the full explanation: this app's `Program.cs` calls `builder.Host.UseSerilog(...)`, which replaces the ASP.NET Core `ILoggerFactory` entirely with Serilog's own pipeline (console sink only, here). Every `ILogger`-based log call — including the exact `"Login succeeded for user {UserId}"` line this task's example query is built around — goes through Serilog, never through the OpenTelemetry Logs pipeline `UseAzureMonitor()` sets up. Only `ActivitySource`/tracing telemetry (HTTP requests, the custom `refresh-token.rotate` span from Task 5) reaches Application Insights today; `ILogger` log lines do not, regardless of what property they carry. Confirmed independently: `union requests, dependencies, exceptions, traces, customEvents | summarize count() by itemType` for the same window returns only `request` (24) and `dependency` (1) — no `trace` rows exist at all, for *any* user, not just this one.
